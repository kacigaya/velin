# Velin backend feasibility

**Verdict: conditional GO for a native hybrid prototype; NO-GO for SDK-only mail parity.**
1. Login and crypto are incomplete: bcrypt panics; mail sender authentication has TODOs [§2, §3].
2. UniFFI lacks mail listing, body/attachment loading, drafts, and sending [§2].
3. Sync, offline state, search, and inbox rules need a client implementation [§3, §6].
4. Native WebAuthn for Velin's own package is UNVERIFIED; upstream uses a browser callback [§3].
5. This ARM host cannot directly run the official Linux x86 NDK tools [§4].
Recommendation: reuse Rust crypto; extend its bindings; port client orchestration to Kotlin [§5].

Audit date: 2026-11-08. Reference HEAD verified as `adccedea76c7049c78c9404332afda50f84bb05a`. All source citations refer to a local Tuta checkout (`TUTA_REFERENCE`) at that commit. ## 5. Recommendation and non-UI module contract

Choose **(c) hybrid**. SDK-only cannot supply the required app. A full Kotlin crypto port would duplicate working sensitive code. Reuse Rust entity/crypto internals through a small Velin-owned binding extension, then implement Kotlin authentication state, mail workflows, sync, storage, and notifications. Keep the reference checkout read-only. This is an engineering recommendation based on §2, not a supported upstream integration promise.

Proposed scope estimate, **UNVERIFIED planning estimate**, excluding UI, generated records, and tests: 8–15 kLOC Kotlin for a limited mail client; 15–30 kLOC for the listed parity surface; 1–3 kLOC Rust bindings/adapters if existing internals cover the needed crypto. Full identity verification/key rotation or external-mail gaps can exceed this. These are not measured port sizes or delivery commitments.
